## 분석 프로세스 이해

### 데이터 분석 프로세스

데이터 분석 프로세스는 정해진 표준은 없음. 사람의 관점에 따라 다르게 구성할 수 있다.
그렇기 때문에 자신만의 프로세스를 정립해가는게 좋음.

1. 비즈니스 이해
2. 데이터 준비: EDA
3. 데이터 전처리: Feature Engineering
4. 모델링
5. 모델 평가
6. 모델 적용

2~5 작업을 반복해서 최종 모델이 결정되면 적용함.
데이터 준비와 데이터 전처리는 혼용되어 사용되기도 함.

### 시나리오 기반 분석 프로세스 이해

1. **분석 주제**
	- 보험사 고객 이탈 예측: 어떤 특성을 가진 고객들이 미래에 이탈할 것인가?
2. **Target 정의(Y)**
	- 이탈 정의: 보험을 해지하거나, 보험료를 2개월 동안 납입하지 않은 고객
3. **Feature 도출(X)**
	- 이탈에 영향을 주는 잠재적 특징 변수
		- 고객 특성(성별, 연령, 직업)
		- 거래 특성 (거래 기간, 납입금액, 미납경험) 등
4. **분석요건 정의**
	- 분석 모집단 정의, 분석 기간 설정
	- 분석 기법 선정 (분류 모델)
5. **분석 모델링**
	- X와 Y의 관계(함수/Rule)를 찾아 가는 과정
	- 지도학습 or 비지도학습
	- 결과물
		- 예측 모델: 예측값(이탈 확률)
		- 모델 평가 결과: 정확도, Feature 중요도

> **분석 기간 종류**
> - 관찰 기간: X 변수 생성 기간, Feature를 수집하는 과거 기간
> - 에측 기간: Y 변수 생성 기간, Target을 판단하는 미래 구간
> - 기준일: 미래를 예측하는 기준 시점

## 데이터 준비

### 데이터 특성 이해

- **타입**
	- 정형: 고정 스키마(행,열), Feature Engineering + ML
	- 비정형: 텍스트/이미지/음성, 대규모 사전학습 모델 + FineTuning, DL
- **크기**
	- Small: 복잡도가 낮은 모델, 비지도 학습, Rule Based
	- Big: 모델보다 학습/추론 인프라, 자동화 설계가 중요
		- 너무 크면 샘플링 전략이 필요함.
- **처리방식**
	- Batch: 복잡한 모델과 Feature 사용 가능
	- Real-time: 모델 정확도보다 "답변 응답 시간, 운영 안정성"이 더 중요

> 데이터 준비는 분석 단계 중 가장 시간이 많이 드는 단계
> (비즈니스 문제 정의 = 매우 중요) + (정의된 목족에 따른 데이터 준비 = 장시간 소요)

### 데이터 처리 용어

- Data Preparation (데이터 준비): 데이터 처리의 포괄적 개념
- Data Preprocessing (데이터 전처리)
	- 모델 개발을 위한 최소한의 데이터 준비 과정
	- 필요한 경우 한번만 진행
		- Data Cleaning, Data Reduction
- Data Wrangling (데이터 랭글링)
	- 모델 성능 향상을 위한 반복적인 과정
		- Sampling, Data Partitioning, Data Binning 등

위 용어들은 혼용되어 사용됨. 그래서 상대방에게 어떤 상황의 처리인지 물어보기

## Feature Engineering
원본 데이터를 모델 성능에 도움이 되는 형태(Feature)로 가공하는 모든 과정

- 모델에 도움이 되는 한 어떤 요소도 Feature가 될 수 있음.
- Feature Extraction: 원본 데이터를 변환, 병합해서 새로운 Feature 생성
- Feature Selection: Feature 중에 유의미한 것만 선정하여 학습 진행
- 데이터를 분석 가능한 형태로 변환하는 과정이고, 그 중에서 모델 성능에 초점을 둔 매우 매우 중요한 단계

### Feature Extraction

- Feature Transformation
	- 기계적 추출 방법
	- 사람의 해석 없이도 생성 가능한 Feature
	- Missing / Normalize / Min / Max
- **Feature Creation(파생변수 생성)**
	- 도메인 지식 기반 추출, 창의력 영역
	- 업무 이해를 바탕으로 의미있는 Feature 추출
	- 가입기간(현재일-가입일) / 소득 대비 부채 비율 (DTI)

![[001_FeatureExtraction.png]]

> 차원의 저주(Curse of Dimensionality)
> = 변수 수가 많아서 생기는 문제
> 
> - 차원이 늘어날수록, 제대로 된 학습을 하려면 필요한 데이터가 기하급수적으로 늘어남.
> - 데이터가 부족한데 차원만 크면 모델은 빈 공간에서도 규칙을 만들게 됨.
> - 실제 패턴이 아닌 빈 공간의 규칙을 만들면 학습 성능은 좋지만, 테스트 성능은 폭락 -> 과적합

### Feature Selection
모형 학습 시간 단축과 모형 안정성 확보를 위해

| 단계     | Feature Selection 과정                           | 담당자       |
| ------ | ---------------------------------------------- | --------- |
| 최초 정의  | 도메인 지식, 경험 및 사례 기반에 의해 후보 Feature 생성 (x1~x100) | 업무 <-> 분석 |
| 신뢰성 검증 | 데이터 기초 탐색으로 데이터 신뢰성 검증                         | 분석 <-> IT |
| 중요도 검증 | 통계 / ML 분석으로 Feature 중요도 검증                    | 분석        |
| 논리성 검증 | 업무 논리적 판단에 의한 검증 (Logical Trend 분석)            | 업무 <-> 분석 |
| 최종 선정  | 최종 Feature 선정 (x2, x7, x9, ...)                | 머신러닝      |

#### Logical Trend 분석
논리성 검증 + 모델 변별력 + 모델 안정성
- 변수의 영향 방향과 크기가 비즈니스 측면에서 "논리적으로 맞는지" 검증하는 과정
- 모델 변별력, 모델 안정성을 같이 판단

### Data Partition
모델 개발을 위해서 데이터셋을 모델 학습 데이터와 모델 평가 데이터로 나누는 것

- TrainSet: 모델 학습을 위한 데이터 셋
- ValidationSet: 학습된 모델을 검증하기 위한 데이터 셋 - 최적의 하이퍼파라미터를 찾는 과정
- TestSet: 모델의 성능 평가

보통 7:3, 8:2 비율로 나눔. 테스트셋이 학습에는 절대 반영 X

#### 방법

- **Hold Out**
	- Random Split: 데이터를 적정 비율로 무작위 분할
	- Timeseries Split: 시간 순서로 데이터 분할
- **Cross Validation**
	- K-fold Cross Validation: 데이터를 K번 나누어 학습,검증을 반복하고 Valid 성능의 평균으로 모델을 검증하는 방법

#### Cross Validation > K-Fold

- 데이터 건수를 동일하게 단순 분할
- 주로 회귀문제에 주로 사용
#### Cross Validation > Stratified K-Fold

- 계층화된 Classification 문제에 주로 사용
- 각 클래스의 비율이 균등하게 유지되도록 데이터 분할
- Class Imbalance 데이터셋인 경우 사용
- 예시: 남, 여의 참여자 수를 분석했을 때 남자가 너무 많으면 어떤 데이터에서는 여자 데이터가 0일 수도 있기 때문에, 여자의 수를 유지하며 남자의 비율으르 균등하게 유지되도록

### Sampling

- **Random Sampling**
	- 확률을 동일하게 추출
- **Partitioned Sampling**
	- TestSet은 그대로 두고, Train에서만 샘플링할 경우
- **Over Sampling**
	- 작은 사이즈의 클래스를 큰 사이즈의 클래스로 균형을 맞추고자 할 경우
	- 작은 데이터를 비교하는 큰 사이즈로 부풀림
	- 경험적으로 모델 성능에 도움이 없었음.
- **Under Sampling**
	- 큰 사이즈의 클래스를 작은 사이즈의 클래스로 균형을 맞추고자 할 경우

## 모델 최적화

최적화: 주어진 조건이나 제약 내에서 최상의 결과를 얻도록 과정이나 방법을 조정하거나 개선하는 과정

모델링 최적화: 모델 학습 과정에서 성능 지표를 개선하고 최상의 성능을 얻는 과정
- 성능 향상: 모델이 정확하고 예측하고 좋은 성능을 발휘하도록 조정
- 일반화 향상: 새로운 데이터에 대해 잘 작동하도록 할 수 있는 모델 개선
- 효율성 증가: 학습 과정의 속도를 높이고, 계산 자원을 효율적으로 사용

### 모델 최적화 전략

![[004_ModelOptimizer.png]]

- 데이터 전략이 성능을 많이 올릴 수 있음.
- 모델 전략은 물론 성능이 올라가지만 한계가 있을 수 있음.

### 하이퍼 파라미터 튜닝 개념

- **파라미터**
	- 모델 내부에서 데이터로부터 학습된 값
	- 작업자에 의해 조정되지 않음
	- 학습 데이터를 통해 자동으로 업데이트
- **하이퍼 파라미터**
	- 모델 외부에서 사용자가 직접 셋팅해주는 값
	- 데이터 분석을 통해 얻어지는 값이 아님
	- 알고리즘을 여러 번 수행하면서 최적의 값을 찾아야 함

### 하이퍼 파라미터 자동 최적화 방법

![[005_hyper-parameter.png]]

| 항목     | Grid Search          | Random Search       | Bayesian Search                     |
| ------ | -------------------- | ------------------- | ----------------------------------- |
| 탐색 방식  | 정의된 범위 내 모든 조합 전수 조사 | 정의된 범위 내 무작위 조합 샘플링 | 이전 결과로 다음 최적점을 예측                   |
| 탐색 효율  | 차원 증가시 비효율적          | 고차원에서 효율적           | 가장 효율적, 적은 시도로 수렴 가능                |
| 최적해 보장 | 격자 안에서는 보장           | 보장 안됨               | 이론상 좋은 해에 빠르게 접근                    |
| 언제 사용? | 하이퍼 파라미터 수가 적을 때     | 하이퍼 파라미터 공간이 넓을 때   | 계산 비용이 큰 모델에 효과적(DL, LGBM, XGBoost) |
- Bayesian(베이시안)을 많이 씀.
- 최적화되는 데이터도 결국 학습셋가지고 하는 것이기 때문에 결과적으로 테스트셋은 항상 좋은 상황만 나오는 것은 아니다.

### Overfitting
모델 과적합

- 학습 데이터에서는 잘 맞는데, 검증 데이터에서는 그렇지 않은 경우를 의미
- 영향 요인: 데이터 특성, 데이터 건수, Feature 개수, 알고리즘 복잡도 등

학습 데이터와 테스트 데이터가 차이가 많이 난다면 과적합이 발생한 것
> TrainSet(0.99), TestSet(0.78) => 과적합 발생

둘 중 좋은 모델은?
TrainSet(0.99), TestSet(0.78) = A
TrainSet(0.80), TestSet(0.75) = B

물론 모델의 정답은 없지만, 그래도 고르자면 A가 더 좋음.
- 과적합이 발생한 것이지, TestSet이 더 좋음.
- 과적합이 발생했다고 문제인 것은 아님.

### Overfitting vs Underfitting

- Overfitting은 학습이 너무 과해서 학습데이터만 잘 맞추는 것
- Underfitting은 학습이 너무 부족해서 학습데이터도 잘 못 맞추는 것

![[006_over_under.png]]

#### 대응방안

| 목록      | Overfitting                         | Underfitting                     |
| ------- | ----------------------------------- | -------------------------------- |
| Date    | 데이터 건수 증가<br>Test와 유사한 Train Set 구성 | 데이터 건수 증가                        |
| Feature | 불필요한 Feature 제거                     | Feature 추가                       |
| 학습 알고리즘 | 알고리즘 Simplify<br>정규화 수행             | 알고리즘 Complexify<br>하이퍼파라미터 범위 늘림 |

### Data Leakage
학습에서 치명적인 함정

- 모델이 예측 시점에 알 수  없는 정보를 학습에 사용한 경우
- 모델 개발 시에는 정확도가 매우 높게 나오는데, 실제 데이터를 넣으면 현저히 성능이 저하되는 이유
- Overfitting은 주로 모델 설계 문제, Data Leakage는 데이터 설계 문제.

보통 테스트 결과가 너무 좋게 나오면 의심을 해야 함.

**Data Leakage**
- Target Leakage
	- Feature에 Target 정보가 직접/간접 포함
- Train-Test Contamination
	- Test 데이터가 학습 과정에 일부라도 노출된 상태

## 모델 평가

모델 평가 지표는 문제 유형, 비즈니스 목적에 따라 선택

문제 유형
- 분류
	- Output
		- Class(1,0): Confusion Matrix (Accuracy / Percision / Recall / F1 Score)
		- Probability(0~1): AUC / LIFT / AUCPR / K-S
- 회귀
	- Output
		- 실수값
			- MAE
			- MSE
			- RMSE
			- MAPE
			- R-Square

### Confusion Matrix
실제 분류값과 예측 분류값의 비교 분류표를 뜻함

![[007_ConfusionMatrix.png]]

![[008_ConfusionMatrixExam.png]]

- 1 - Recall: 실제 양성중 놓친 비율 - 미탐
- 1 - Precision: 양성 예측 중 틀린 비율 - 오탐

모델 성능 평가는 평가지표 절대값보다 "비교 기준"이 더 중요

- Baseline Model: 모델 성능 평가 시 비교 대상으로 사용하는 모델
- Navie Model: 학습 없이 가장 단순한 규칙만으로 예측하는 모델

### AUC(AUROC, ROC-AUC)
분류 임계값을 0부터 1까지 변화시키면서 모델의 성능을 종합적으로 평가하는 지표

AUC = ROC Curve 아래의 면적(Area Under the ROC Curve)
ROC 곡선: 분류 임계값을 0에서 1까지 변화시킬 때 모델의 예측 성능 변화를 나타낸 그래프

### LIFT
전체 집단에 비해 특정 집단의 예측력이 향상된 정도

- 직관적인 평가지표로, 예측 Score 상위 고객을 선별하여 업무에 활용할 때 유용
- 상위 K건의 Positive 비율이 무작위 대비 몇 배인지 나타내는 지표

### AUC & LIFT

AUC는 전체 집단의 모형 성능을 평가하고, LIFT 로 관심 집단의 성능을 평가

## Regression 모델 평가 지표

### 회귀모형 성능 평가

![[011_Regression.png]]

- MAPE: 오차의 절대값을 실제값으로 나눈 후 모두 더한 다음 데이터 크기로 나눈 값
	- 단위가 다른 모델의 비교할 수 있음.
	- 0값 문제: 실제 값이 0일때 MAPE를 계산할 수 없음
	- 데이터 값이 매우 작을 때 -> MAPE가 무한대로 발산
	- 대체재로 sMAPE(실제값과 예측값의 차이를 두 값을 평균으로 나누어 대칭적인 오차 계산)
- MAE: 오차의 절대값을 모두 더한 다음 데이터 크기로 나눈 값
- R^2: 회귀모델에서 독립변수가 종속변수를 얼만큼 설명해 주는지 가리키는 지표
	- 1에 가까울 수록 성능이 좋고, 음수값이 나오면 Y 평균값으로 예측한 것 (Navie 모델)보다 못한 것.

## 모델 해석

### 모델 해석이 중요한 이유

ML/DL 모델은 블랙박스 모델 - 내부 동작을 이해하기 어려움.
통계적 모델은 계수를 통해 인과관계 설명 가능

`Explainable AI(XAI)` 기술을 통해 블랙박스 모델을 해석할 수 있음. 그 중 `SHAP`은 가장 강력하고 이론적으로 검증된 도구

### SHAP

- Feature Importance: 변수의 평균적인 영향력을 보여줌. 각 특성이 모델에 미치는 절대 영향도를 파악가능
- Feature Impact: 변수의 영향도와 각 변수가 모델에 영향을 주는 분포를 확인
- Feature Dependence: 각 특성별 Target과의 관계 패턴을 보여주는 것으로, 특성 간 상호작용도 확인가능

## 모델 모니터링

### Model Drift
학습 환경과 운영 환경의 차이로 시간이 지남에 따라 모델의 성능이 저하되는 현상

- Data Drift
	- 입력 데이터의 변화 (X 분포 변화)
- Prediction Drift
	- 모델 출력의 변화 (Y 분포 변화)
- Concept Drift
	- 데이터 관계의 변화 (X -> Y Relationship)

#### Data Drift
모델에 입력되는 데이터의 통계적 분포가 학습 시점과 유의미하게 달라지는 현상

- 사용자/환경 변화
- 계절성 및 트렌드
- 데이터 파이프라인 이슈

#### Prediction Drift
모델이 출력하는 예측값의 통계적 분포가 기준 시점과 유의미하게 달라지는 현상

- 결과론적 지표
	- Data Drift 나 Concept Drift가 발생했을 때, 그 결과로서 변하는 경우가 많음
- 주요 예시
	- 스팸 탐지율 급증 (5% -> 20%)
	- 긍정/부정 예측 비율 역전

#### Concept Drift
입력 데이터와 정답(Target) 간의 상관관계(패턴)가 변해서, 기존 모델이 더이상 유효하지 않은 현상

- 거시 환경 변화
- 비즈니스 프로세스 변경
- 주요 예시
	- 경쟁사 등장으로 이탈 요인 변경
	- 경기 침체로 인한 소비 패턴 변화

### 모델 드리프트 대응 전략

- Data Drift: Feature 변경없이 가중치만 조정 (Re-training)
- Prediction Drift: 의사결정 위한 예측 확률 기준값 조정 (Threshold Adjustment)
- Concept Drift: EDA부터 Feature 생성등 모델 재구축 (Re-modeling)

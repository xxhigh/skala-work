## 생성형 AI 이해

### AI 발전 단계

규칙기반(If-then) -> 머신러닝(ML) -> 딥러닝(DL) -> 생성형 AI

판별형 - 맞다 아니다를 사람이 정해줌. (딥러닝까지)
생성형 - 미리 학습한 모델을 기반으로 스스로 판단.

예전에는 "데이터를 모아 모델을 새로 가르치는 일"이었다면 지금은 "이미 똑똑한 모델에게 잘 설명하는 일"

### 생성형 AI의 기술 구조

#### 사용자의 요청을 입력한 뒤 결과가 나오기까지의 처리 순서

1. 사용자 요청 작성
2. 서비스 계층
3. 모델 계층 (LLM, Diffusion Model, ASR‧TTS, Video Diffusion)
4. 생성 결과
5. 사용자 검토

### LLM 기본 동작 원리

1. 토큰화
	- 문장을 토큰(단어 조각)으로 분해
2. 확률 예측
	- 앞 맥락(Context)을 보고 다음 토큰의 확률을 계산 (Transformer, Attention)
3. 생성‧반복
	- 확률이 가장 높은 토큰을 골라 이어 붙이고 1~3 반복
	- 종료 토큰(EOS)이 나오거나 최대 출력 길이에 닿으면 멈춤


### 토큰과 토크나이저

토크나이저: 텍스트를 토큰으로 변화시키는 규칙
토큰화: 쪼개는 과정
토큰: 모델이 처리하는 텍스트 최소 단위

토큰 = 비용이기 때문에, 토큰을 줄이는게 목표

### 할루시네이션

#### 사실이 아닌데도 그럴듯하게 지어내는 현상.

1. LLM은 '사실 조회'가 아니라 다음에 올 그럴듯한 말을 확률로 이어 붙임.
2. 그래서 모르는 것도 '모른다'가 아니라 통계적으로 그럴듯하게 채워 넣음
3. 학습 시점 이후, 전문 영역, 자료가 드문 내용일수록 위험이 커짐.

#### 완화방법

1. 근거 ‧ 출처 요구
2. 맥락 제공
3. RAG
4. 사람 검증

### 생성형 AI 활용 시 유의점

1. 사실 검증 - 수치, 인용은 반드시 원문 확인
2. 정보 보안 - 고객, 개인, 기밀 정보는 프롬프트에 넣지 않기(부득이 사용 시 마스킹 필수)
3. 저작권 라이선스
4. 편향 인지 - 인터넷 글을 학습하기 때문에 다수 의견, 특정 집단의 관점이 정답처럼 나오기 쉬움

## 프롬프트 엔지니어링

### 좋은 프롬프트의 조건

1. 명확성: 무엇을 원하는지 모호하지 않게
2. 구체성: 분량,형식,조건을 구체적으로
3. 맥락: 판단에 필요한 배경,자료,예시를 함께 제공

### 프롬프트의 종류

- 시스템: 서비스 제공자가 설정 - 정체성, 말투, 금지사항, 안전규칙등
- 개발자: 서비스를 만드는 쪽이 넣는 업무 규칙, 출력 형식, 도구 사용 지침
- 유저: 최종 사용자의 그때그때의 요청

```
messages = {
	{"role": "system", "content": "나는 통신사 상담 AI다"},
	{"role": "developer", "content": "답변은 JSON, 근거 문서 ID 포함"},
	{"role": "user", "content": "요금이 왜 올랐어?"},
}
```

User의 요청이 개발자나 시스템의 지침과 어긋나면 유저의 요청은 뮤시함.

### 프롬프트 5가지 요소

- 역할
- 목적
- 맥락
- 제약
- 출력형식

### Zero-shot & Few-shot

Zero-shot: 예시 없이 지시만 준다. 간단하고 빠르지만 출력이 일정하지 않음.
예시) "배송이 느리다.", "다름 리뷰의 감성을 긍정/부정으로 분류해"

Few-shot: 원하는 입력 -> 출력 예시를 보여주고 같은 형식으로 답하게 한다. 형식,톤,기준을 말 대신 예시로 고정
예시) 리뷰: "품질 최고예요" -> 긍정, 리뷰: "다시 안 사요" -> 부정

### CoT - 단계적 추론

답을 바로 내지 말고 중간 추론 과정을 단계별로 거치게 유도 -> 복잡한 문제의 정확도 향상.

### 역할 부여(페르소나), 구조화, 출력형식

페르소나 - 답의 관점,전문성,용어가 달라짐
구조화 - 지시,자료 예시를 구분자로 분리 -> 모델이 혼동하지 않음.
출력형식 - 표,json 등 형태를 지정 -> 자동화 쉬움

### 샘플링 파라미터

LLM은 다음에 나올 단어의 확률을 계산한 뒤 그 중 하나를 골라 문장을 잇는 방식을 조절하는 설정값
temperature: 값을 올리면 평탄(다양), 내리면 뾰족(일관)하게 확률분포를 바꿔 다양성 조절 (0~0.3 일관,사실)
Top-p: 확률 높은 순으로 누적활률 p까지만 후보로 사용 (0.9 누적확률 90%까지, 1.0 전체 후보)
Top-k: 확률 상위 k개 후보 중에서만 다음 토큰 선택 (k=1 확률 1위 단어만(결정적) k값이 높아지면 다양성도 높아짐)
Max tokens: 생성할 최대 토큰 수 (짧게 = 비용이 낮아지면 속도가 빨라짐. 답변이 문장 중간에서 끊길 수 있음.)

### 프롬프트 반복 개선 사이클
1. 작성
2. 실행
3. 평가
4. 개선
를 순서대로 반복해서 최상의 결과를 얻기위해 반복

## 컨텍스트 엔지니어링

### 프롬프트의 한계
1. 최신성: 학습시점 이후의 사실은 모름
2. 사내,비공개 지식: 사내 비공개 약관, 메뉴얼, DB는 모델이 학습하지 않음.
3. 긴 맥락: 수백 페이지 문서를 다 넣어도 그대로 쓰이지 않음.
4. 외부 도구,실시간: 정확한 계산, 실시간 조회, 시스템 실행은 언어 생성만으로 불가

**해법 방향**: 1. 필요한 맥락을 쥐어준다. -> Context Engineering  2. 도구를 쓰게 한다. -> AI Agent

### 맥락 설계

1. 지시
2. 기억
3. 지식
4. 도구 결과
5. 현재 질문

컨텍스트 윈도우: 모델이 한 번에 볼 수 있는 입력의 최대 크기. 무엇을 넣고 뺄지 선별이 핵심.

### 메모리 & 컴팩션

대화,맥락이 길어질 때, 반드시 보존할 핵심 정보와 요약해도 되는 정보를 구분해 다음턴의 맥락을 구성한다.

### RAG 동작 흐름

사내 문서 수집 -> 청킹(검색 단위로 자르기) -> 임베딩(의미 좌표로 변환) -> 벡터DB 저장 = 지식베이스 완성

1. 질문: 사용자 입력
2. 검색: 지식베이스 조회 - 질문을 임베딩으로 바꿔 유사 조각 상위 k개 검색 (Top-k)
3. 맥락 주입: 찾은 문서를 질문과 함께 넣기
4. 생성: 근거 기반 답변

### AI 기능, Workflow, 에이전트

AI기능: 다음 단계는 사람이 정한다. 한 번 시키고 한 번 받음
워크플로: 다음 단계는 개발자가 코드로 미리 정해 둔다. (대부분의 AI 서비스가 여기)
에이전트: 다음 단계를 AI가 스스로 정한다.

### 하네스 엔지니어링

AI Agent는 계획 -> 도구 사용 -> 결과 관찰 -> 재시도를 스스로 반복
다만, LLM 하나만으로는 이 루프가 돌지 않음.
1. 실제로 조회할 수단이 없음
2. 앞 단계를 기억하지 못함
3. 멈출 시점을 모름
4. 잘못된 행동을 막을 장치가 없음

위 4가지 결핍을 바깥에서 채워 주는 실행 환경을 설계하는게 하네스 엔지니어링
즉, 에이전트 실행 환경(도구,권한,제어 루프, 메모리)을 설계하는 일.

### 하네스 설계 원칙

공식은 아님(최진철 교수님이 정리해본 것.)

- 가독성
- 기계적 강제
- 점진적 공개
- 규칙 파일

### 도구 연결(MCP 와 Function Calling)
Function Calling: 도구의 이름, 설명, 입력 형식을 Ai에게 알려 주면, 어떤 도구를 어떤 값으로 부를지 스스로 골라 요청

Model Context Protocol: 도구,데이터 소스를 MCP 서버로 한 번 만들어 두면, 이를 지원하는 여러 AI 도구가 같은 방식으로 연결됨.
